# 要件定義書

## 1. アプリケーションの目的

飲食店オーナーがオンラインで申し込むと、その店舗専用の「管理画面」と「お客様用注文画面」が自動的に作成される、**マルチテナント型のモバイルオーダー＆レジ SaaS**。

キャッシュレジスターの代替と、スマートフォンを使ったセルフオーダーの両方をカバーし、スタッフの省力化と顧客体験の向上を同時に実現する。

---

## 2. 登場人物（アクター）

| アクター | 説明 |
|---|---|
| **店舗オーナー** | システムへの申込みを行い、店舗アカウントを開設する責任者 |
| **店舗スタッフ** | 管理画面・会計画面を使って日常業務（メニュー管理・注文確認・会計）を行う |
| **来店客** | 席の QR コードをスマホで読み取って注文・会計要求を行う |

---

## 3. 4 つの画面

### ① 申込み画面（店舗登録）

- **アクター**: 店舗オーナー
- **役割**: 店舗名とメールアドレスを登録し、Magic Link メール認証を経て管理画面へのアクセスを開始する。
- **主な操作**:
  - 店舗名・メールアドレスの入力・送信
  - 受信した Magic Link メールのリンクをクリックしてメール認証を完了

### ⑤ ログイン画面（Magic Link）

- **アクター**: 店舗オーナー / 店舗スタッフ
- **役割**: 登録済みのメールアドレスに Magic Link を送信し、リンクをクリックして管理画面にログインする。パスワード不要。
- **主な操作**:
  - メールアドレスの入力・送信
  - 受信した Magic Link メールのリンクをクリックしてログイン

### ② 店舗管理画面

- **アクター**: 店舗スタッフ
- **役割**: メニュー管理・座席管理・注文状況のリアルタイム確認
- **主な操作**:
  - メニューカテゴリの追加・編集・削除
  - メニュー商品の追加・編集（商品名・価格・提供状態）・削除
  - 座席の追加・削除、座席ごとの QR コード発行
  - 各座席の現在の注文一覧を確認（未提供の品の確認）
  - 個々の注文明細を「提供済み」にマーク

### ③ 顧客注文画面（モバイルオーダー）

- **アクター**: 来店客
- **役割**: スマホで QR コードを読み取った後に表示される、注文と会計要求の画面
- **主な操作**:
  - 現在のメニュー一覧を閲覧
  - 商品を選択して注文を送信（複数回送信可能）
  - 自分が注文した内容と合計金額の確認
  - 「会計をお願いする」ボタンで会計要求を送信

### ④ 会計・レジ画面

- **アクター**: 店舗スタッフ
- **役割**: 会計要求が届いた伝票の注文履歴と合計金額を確認し、支払い完了処理を行う
- **主な操作**:
  - 会計要求中の伝票一覧を確認
  - 伝票の注文明細と合計金額の確認
  - 「会計完了」ボタンで決済を完了させ、伝票をクローズ

## 4. 基本業務サイクル

以下の 5 ステップが**一連の流れとして破綻なく機能**することを保証する。

```
[Step 1: 導入]
  オーナーが ① 申込み画面 で店舗名・メールアドレスを入力する
      ↓
  stores テーブルにレコード作成（status = "pending"）
  Magic Link メールを送信（magic_link_tokens に purpose = "signup" で記録）
      ↓
  オーナーがメールの Magic Link をクリックする
  stores.status = "active" に更新、sessions レコード作成・session_token Cookie 発行

[Step 2: 準備]
  スタッフが ② 管理画面 でメニューを登録する
      ↓
  menu_categories / menu_items テーブルにレコード作成
  seats テーブルに座席を追加し qr_token 発行
  QR コードを印刷して各席に配置

[Step 3: 注文]
  来店客がスマホで QR コードを読み込む
      ↓  /order/:qrToken でアクセス
  seats テーブルで席を識別、
  当該席のアクティブな orders レコードを取得（なければ作成）
  来店客が ③ 顧客注文画面 から料理を注文
      ↓
  order_items テーブルに明細追加（status = ordered）

[Step 4: 提供]
  スタッフが ② 管理画面 で新規注文を確認（ポーリング or WebSocket）
      ↓
  料理を提供後、管理画面から order_items.status = served に更新

[Step 5: 会計]
  来店客が ③ 顧客注文画面 から「会計をお願いする」を送信
      ↓
  orders.status = payment_requested に更新
  スタッフが ④ 会計・レジ画面 で合計金額を確認して「会計完了」
      ↓
  payments テーブルにレコード作成
  orders.status = paid に更新（伝票クローズ）
```

## 5. 初期フェーズ（MVP）のスコープ

### ✅ MVP に含む

| 機能 | 詳細 |
|---|---|
| 店舗登録・認証 | 店舗名＋メールで申込み、Magic Link で認証してセッションを発行 |
| メニュー管理 | カテゴリ＋商品の CRUD |
| 座席管理・QR 発行 | 席の追加・削除、QR コード表示 |
| モバイルオーダー | QR から注文、会計要求 |
| 注文確認・提供管理 | 管理画面でリアルタイム（ポーリング）確認、提供済みマーク |
| 会計処理 | 合計金額確認、現金会計完了 |
| マルチテナント分離 | 全データが store_id で分離されること |

### ❌ MVP に含まない（後フェーズ）

| 機能 | 対象フェーズ |
|---|---|
| トッピング・大盛りなどのオプション | Phase 2 |
| 店舗ロゴ・テーマカラーのカスタマイズ | Phase 3 |
| クレジットカードなどオンライン決済 | Phase 4 |
| WebSocket によるリアルタイム通知 | Phase 4 |
| パスワードによる認証 | 未定 |
| 売上分析・レポート | 未定 |

## 6. 将来拡張の余地（設計上の配慮事項）

以下の拡張が**追加・改修のみで済む**よう初期設計の段階から余地を確保する。

### 6.1 メニューのカスタマイズ機能（トッピング・大盛り）

- `menu_items` に対して `option_groups`（例: サイズ、トッピング）と `options`（例: 大盛り +100 円）を後から関連付けられるよう、外部キーの受け口を残す
- `order_items` に `order_item_options` を追加することで、注文時の選択内容を保存できる設計

### 6.2 店舗ごとのロゴ・テーマカラー変更

- `stores` テーブルに `logo_url` / `theme_color` カラムを将来追加可能
- 顧客注文画面・申込み完了画面を CSS 変数ベースで実装し、テーマ適用が容易な構造

### 6.3 オンライン決済

- `payments` テーブルの `method` カラムを `cash`（初期）から `card` / `qr` などに拡張可能
- 決済処理を `src/lib/payment/` に切り出し、PSP（Stripe など）への差し替えを局所化

## 7. 非機能要件

| 項目 | 方針 |
|---|---|
| **対応環境** | 顧客注文画面はモバイルファースト（主要スマートフォンブラウザ対応）。管理画面は PC ブラウザを想定 |
| **パフォーマンス** | 注文送信・会計要求のレスポンスは 2 秒以内を目標 |
| **セキュリティ** | 管理画面は Magic Link 認証＋`session_token` Cookie（HttpOnly）による保護。顧客注文画面は `qr_token`（席トークン）でアクセス制限。HTTPS 必須（Cloudflare 標準）|
| **スケーラビリティ** | Cloudflare Workers + D1 のグローバルエッジ配信。マルチテナント構造で新店舗の追加がデータ追加のみ |
