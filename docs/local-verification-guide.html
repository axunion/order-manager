全体の流れ（概観）

このアプリには 2 種類のユーザー と 2 つの認証経路 があります。 店舗スタッフ は Cookie で保護された管理画面を使い、 来店客 は QR コードのトークンのみで注文画面にアクセスします。

ポイント
店舗登録・認証が全操作の前提です。 管理画面（/admin/*）にアクセスするには有効な session_token Cookie が必要です。 この Cookie は Magic Link メールのリンクをクリックして認証が完了した時点で発行されます（GET /api/auth/verify）。 Cookie なし・無効トークンの場合は自動的に /login にリダイレクトされます。

ローカル開発での近道: pnpm seed:dev を実行するとメールなしで管理画面に入れるシードアカウントが作成されます（→ ステップ①参照）。
2

認証・ルーティングの仕組み

🔐 管理画面の認証（Cookie 方式）

リクエストが /admin/* に来るたびに middleware.ts が動作します。

  1. session_token Cookie を読む
  2. D1 DB で sessions テーブルを検索・有効期限確認
  3. stores.status = "active" を確認
  4. 有効 → Astro.locals.store にセット
  5. Cookie なし / 無効 / 期限切れ → /login へリダイレクト
  6. status = "pending" → /register/check-email へリダイレクト
セキュリティ
Cookie は HttpOnly（JS からアクセス不可）、SameSite=Lax（CSRF 対策）。 ローカル dev では HTTP のため Secure 属性は省略されます（本番 HTTPS では自動付与）。

📱 顧客注文画面の認証（URL トークン方式）

Cookie は使いません。QR コードの URL 自体がアクセスキーです。

  1. QR コードに /order/:seatToken URL が埋め込まれる
  2. ページサーバーサイドで getSeatByQrToken(db, seatToken) を呼ぶ
  3. ヒット → 座席情報を OrderScreen に渡す
  4. ヒットしない → 「ページが見つかりません」を表示（リダイレクトなし）
注意
QR トークンは店舗登録後に 管理画面で座席を作成して初めて 生成されます。 座席なしでは顧客注文画面は存在しません。
3

起動と DB 準備

前提条件

  • Node.js 20+ / pnpm がインストール済み
  • 依存パッケージインストール済み（pnpm install）

① DB のリセット＆マイグレーション適用

初回または DB を白紙から始めたい場合に実行します。

# ローカル D1 をリセットして最新マイグレーションを適用 pnpm db:reset
注意
このコマンドはローカルの DB を全削除します。本番 DB には影響ありません。

② 開発サーバーの起動

pnpm dev # → http://localhost:4321 で起動

wrangler が Cloudflare Workers ランタイムをエミュレートします。ポートは 4321（デフォルト）。

4

ステップ①：店舗登録（必須・最初に行う）

前提：認証を完了しないと管理画面にアクセスできません
/admin に直接アクセスしても /login にリダイレクトされます。 ローカル開発では pnpm seed:dev（近道）か、下記フローのどちらかで認証してください。

近道: ローカル開発用シードアカウント（推奨）

pnpm seed:dev を実行 → dev@localhost の店舗 + セッションが D1 に作成される
出力された session_token 値を控える
DevTools → Application → Cookies → Name: session_token、Value: <出力値>、Path: / で追加
http://localhost:4321/admin にアクセスして管理画面が表示されることを確認

本フロー: 申込み〜Magic Link 認証（本番同等の確認）

ブラウザで http://localhost:4321/register を開く
「店舗名」と「メールアドレス」を入力する（例：山田珈琲店 / 自分のメールアドレス）
「登録する」ボタンをクリック → POST /api/stores が実行される
成功すると http://localhost:4321/register/check-email へリダイレクトされる（この時点で Cookie はまだ発行されない）
受信した Magic Link メールのリンクをクリック → GET /api/auth/verify?token=… が実行される
認証成功 → session_token Cookie が発行され、http://localhost:4321/admin へリダイレクトされる

確認ポイント

確認事項確認方法期待値
申込み後に案内ページへ遷移したか URL バーを確認 /register/check-email が表示されている（Cookie はまだない）
API レスポンスが 201 か DevTools → Network → /api/stores Status: 201、body に {data: {id, name, slug}}。Set-Cookie ヘッダーはない
Magic Link 認証後に Cookie が発行されるか メールのリンクをクリック後 → DevTools → Application → Cookies session_token が存在し、HttpOnly にチェックが入っている
認証後に管理画面へ遷移したか URL バーを確認 /admin が表示されている

ステップ②：管理画面の確認

管理画面には 4 つのサブ画面 があります。メニュー登録と座席作成を先に行う必要があります（注文画面が機能するために必要）。

メニュー管理 — /admin/menu

「カテゴリ追加」でカテゴリを作成（例：ドリンク）
カテゴリ内に「商品追加」でメニューを登録（商品名・価格）
顧客注文画面で表示されることを後で確認する

座席管理 — /admin/seats

「座席追加」で座席を作成（例：テーブル1）
QR コードが表示される → URL を控える（/order/:seatToken）
この URL が顧客注文画面へのリンクになる
重要：middleware.ts による保護の確認
シークレットウィンドウ（Cookie なし）で http://localhost:4321/admin に直接アクセスしてください。 /login へリダイレクトされれば認証が正しく動作しています。
6

ステップ③：顧客注文画面の確認

前提
座席管理で 少なくとも1つの座席が作成されている必要があります。 QR トークンは座席作成時に自動生成されます。

操作手順

/admin/seats で表示された QR コードの URL をコピー（例：http://localhost:4321/order/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx）
別タブ（または別ブラウザ） でその URL を開く。これが来店客視点です
メニューが表示されること・商品を選んで「注文する」が送信できることを確認
注文後、管理画面 /admin/orders に注文が届いていることを確認
顧客注文画面で「会計をお願いする」を送信 → /admin/checkout に会計要求が届くことを確認

セキュリティ確認ポイント

ローカル確認でも以下のセキュリティ設計が機能していることを DevTools で検証できます。

確認項目手順期待する結果担保する脅威
HttpOnly Cookie DevTools Console で document.cookie を実行 session_token が表示されない XSS によるトークン盗用
未認証アクセス拒否 シークレットウィンドウで /admin に直接アクセス /login にリダイレクトされる Cookie なし直接アクセス
無効トークン拒否 DevTools で Cookie の値を書き換えてから /admin にアクセス /login にリダイレクトされる トークン偽造
未認証店舗のアクセス拒否 stores.status = "pending" のセッションで /admin にアクセス /register/check-email にリダイレクトされる メール未確認状態での管理画面進入
無効 QR トークン ブラウザで /order/invalid-token-xxxxx にアクセス 「ページが見つかりません」が表示される（リダイレクトなし） 不正 QR アクセス
テナント分離 API レスポンスを DevTools → Network で確認 自店舗のデータのみ返却される 他テナントデータ漏洩
ローカル環境の注意点
ローカル dev（wrangler dev）は HTTP で動作するため、Cookie の Secure 属性が付与されません（本番 HTTPS では自動付与）。 これは意図的な設計です（src/lib/auth.ts の SESSION_TOKEN_COOKIE 定数参照）。

トラブルシューティング

症状原因対処
/admin を開くたびに /login に戻る session_token Cookie がない、または DB がリセットされてセッションが無効になった pnpm db:reset && pnpm seed:dev → 出力されたトークンを Cookie にセット
顧客注文画面に「ページが見つかりません」 seatToken が無効（DB がリセットされた等） 管理画面 /admin/seats で座席を再作成し、新しい QR URL を使う
メニューが注文画面に表示されない メニュー未登録、または販売停止状態 /admin/menu でメニューを登録・有効化する
サーバーが起動しない ポート競合または wrangler の設定エラー pnpm dev のログを確認。ポート 4321 が使用中であれば終了させる
登録フォームで「通信エラー」 開発サーバーが未起動 pnpm dev でサーバーを起動してから再試行
